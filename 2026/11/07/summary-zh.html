Jev 路由到 Opus 实现同等精度成本降 4 倍 ⭐️ 8.0/10

Hightouch 博客展示模型级联路由：Jev（Qwen 2.5 32B）作为路由器，仅在需要时升级调用 Claude Opus。实测达到 Opus 级精度，成本降至 1/4，输入 token 减少 65%。Jev 的置信度评分可靠，低于阈值时触发升级。

hackernews · theanomaly · 11月6日 19:48 · 社区讨论

「背景」 LLM-as-a-Judge 让大模型充当评估器，但推理型 Judge 昂贵且慢。ArXiv 论文 JEV-as-a-Judge 提出仅输出标签概率的轻量决策模型 Jev，按置信度决定是否升级到推理 Judge。Hightouch 将该级联用于身份解析，Jev 处理易例，低置信时转交 Claude Opus。

「影响」 编码代理 Memdoor 实测：读取密集型任务输入 token 减少 63-65%，模式调用减少 40-45%。适用于文件读取、grep 大文件夹等场景。

「社区讨论」 用户 xlayn 报告 Qwen 3.8 27B 能从 Haiku/Sonnet/Opus 获取良好答案。guregodevo 确认 Jev 在编码代理中成为主流路由方式。andai 指出关键在于 Jev 置信度评分可靠，Luna 虽更准但置信度不可靠无法做回退决策。

Boson AI 发布 45B MoE 全双工模型 Higgs Realtime Duplex ⭐️ 8.0/10

Boson AI 发布 Higgs Realtime Duplex，45B MoE 全双工模型，可同时处理音频、视频、文本流，后台并行推理、工具调用与任务委派。非开放权重，仅提供 Duplex API 等待名单；早期基于轮次的 Higgs Realtime 已可用。架构将所有模态切为 160 ms 固定块：音频输入 1 token/块 (6.25 tokens/s)，音频输出 2 tokens/块 (12.5 tokens/s)，视频输入每 6 块一帧 (~12 tokens)，人脸输出 2 latents/块，文本同步输入输出，静音也编码为块供模型决定回声/打断/静默。综合吞吐约 2.6K tokens/分 (音视频)，含思考达 2.6K–5K tokens/分。零样本部署：短参考音频定音色、单张参考图定人脸、文本提示定行为。音频用因果 flow-matching 解码器 (2 帧/块)，人脸用条件因果 DiT。训练：从文本预训练 LLM 起步，自建 H100 集群 (Megatron) 继续预训练 ~2T tokens 文本/音频/视频；后训练用多教师在线策略蒸馏，专家教师经 RL (含 GRPO) 训练对话、时序、委派、任务完成，再在模拟环境 (真实时序、打断、重叠语音、背景噪声) 自我改进循环。基准对比 (实验室复现)：Big Bench Audio 98.9 (vs TML 276B 96.5, OpenAI 97, Google 98)，Audio MultiChallenge APR 44.9 (vs 43.4/48.5/36.1)，Full-Duplex-Bench v1.5 75.5 (vs 77.8/80.1/54.3)，QIVD 流式 56.0 (vs 54.0/58.2/56.1)，ProactiveVideoQA PAUC 31.9 (vs 33.5/25.0/–)，τ-Voice pass@1 69.8 (vs –/74.5/68.6)，IFEval 94.1 (vs 89.7/95.2/90.0)。OpenAI 最佳设置在 7 项中 5 项领先 1–5 分。团队结论：规模、数据、训练比参数量更关键；刻意保持中等规模，目标模型小时成本约为人工小时成本 1/10。

reddit · r/MachineLearning · /u/Cali_Cobarde · 11月6日 20:23

「背景」 Boson AI 此前发布过基于轮次的 Higgs Realtime 模型，采用传统「听完→思考→说话」流水线。全双工架构改为并行处理音频、视频、文本流，模型可在输出语音的同时持续接收输入、后台推理与调用工具。

「影响」 Duplex 仅提供 API 等待列表，权重不开源，开发者无法立即自行部署或复现；现有可用的是上一代基于轮次的 Higgs Realtime。若基准性能在生产环境成立，模型推理成本约为人工每小时成本的 1/10，可能降低实时多模态交互应用的运营门槛。

「社区讨论」 Reddit 评论区主要围绕闭源/仅 API 等待名单、基准可复现性、与 OpenAI/Google 实时模型的实际差距展开。有用户质疑未开放权重限制学术复现，也有开发者关注 160 ms 块延迟对实际交互体验的影响。无实质性技术细节补充。

GitHub Rubicon 架构实现 7200 推送/秒 ⭐️ 8.0/10

GitHub 发布代号 Rubicon 的新 Git 存储架构，内部测试支持 5000 个 AI 智能体并发操作单个仓库，每秒处理 7200 次推送，读取延迟保持低水平。架构将 Git 对象存入 Azure Blob Storage，引用状态由 Ref-CAS 管理，虚拟副本处理读写，后台节点压缩数据包。目前处于有限私有预览阶段，将逐步扩大推广范围。

telegram · zaihuapd · 11月7日 14:12

「背景」 GitHub 此前的 Git 存储依赖单机文件系统与多副本复制，难以支撑数千 AI 智能体并发向同一仓库推送的新负载。Rubicon 将对象数据迁移至 Azure Blob Storage，引用状态交由 Ref-CAS（引用比较并交换）原子操作管理，虚拟副本分离读写路径，后台再做 packfile 压缩，从而突破原有写入吞吐瓶颈。

「影响」 大规模 AI 智能体协作场景下，单仓库推送吞吐量提升至 7200 次/秒，解决传统 Git 存储在高并发写入下的性能瓶颈。开发者可预期未来 GitHub 支持更大规模自动化工作流，但目前仅限私有预览，通用可用时间未公布。
